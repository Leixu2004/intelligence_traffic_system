## [04:06] 第 06 页 · 关键指标

指标我分三档，混用是这类汇报最常见的错误。

第一档，现场实跑的预测。独立测试集一千四百六十七个窗口，R² 等于 0.8644，过了课件 0.85 的线，这条敢说达标；同一份数据同一个模型，MAE 是 9.81，要求小于 5，记 FAIL，参照是同数据朴素基线 10.53。R² 过线而 MAE 未过，说明抓住了趋势没压住绝对误差，我不换口径凑数。

第二档，实时计算的集群实测。灌入八十九条事件，速度统计十三行、预警三十八行，四级分布绿十七黄十九红一紫一；两个作业检查点三十九次全部完成、零失败，语义 EXACTLY_ONCE，由 Flink UI 加接口复核过。

第三档讲口径。车牌模型单次推理平均 14.88 毫秒，这是 CPU 上的模型内核耗时，口径 model_only，不等于端到端，不用它交全链路小于 200 毫秒那条。本机 vLLM 推理成功，但只有两次请求、只有 1.5B 模型，这一格写 NOT_VERIFIED。

## [06:57] 第 08 页 · 工程难点

这页说明东西是在真机上跑出来的，不是在文档里，挑三个讲。

端口抢占：本机另一套 Postgres 占着 5432，我没改本机服务，而是把宿主端口做成变量、默认让到 55432，容器内仍是 5432，Flink 走 Docker 网络不受影响。

Git Bash 的路径改写：挂载 /models 时被改成 Windows 路径，容器起得来但读不到权重，解法是带 MSYS_NO_PATHCONV=1。

这条最容易骗人：集成链路不把 API Key 显式置空，配置会拿云端密钥补默认端点，请求悄悄跑到云上，表面本地推理成功、实际云端在算。这个约束我写进复现命令，报告标了行号。

# 附：追问应答（背下来，别念稿）

**问：这些数据是真的吗？**
答：分三档。现场实跑的、标了 simulation 等于 true 的演示数据、以及 BLOCKED 未验证的。这个分类不是我口头说的，大屏和接口响应里就打印了 source 和 verified 字段，老师可以直接看。

**问：MAE 没达标，为什么还用这个模型？**
答：R² 和 MAE 是两个维度，一个看趋势解释力，一个看绝对误差。达标线来自课件验收表，未达我就记 FAIL，并把朴素基线 10.526 和模型 9.8123 一起给出来，让老师看到模型确实优于基线、但离要求还有多远。

**问：为什么用 1.5B 的模型，不用 7B？**
答：本机显存 8 GB，装不下 7B 的 FP16，权重本身就约 14 GB。换小模型可以跑通服务化链路，但我在报告里明确写了 1.5B 的结果不能代表 7B，也不把云端调用冒充本地推理。

**问：天河的路况是真实现场采集的吗？**
答：不是。卡口名是天河的地名，坐标是演示化布置，数值来自公开研究数据。要真实路况需要高德的 JS Key，未配置时页面一律显示演示拓扑，不虚标。这一页证明的是渲染链路和来源标注正确。

**问：和课件里的示例数字差在哪？**
答：课件的 1.2 秒、QPS 62、mAP 0.92、覆盖率 85% 都是示例数字。我只引用被文件或日志证实的值；课件要求而我没做的，在报告 4.2 逐行列成了九项。

**问：覆盖率 28.78% 你觉得合格吗？**
答：不合格，门禁那一项就是 FAIL，我没有给它找台阶。补测优先级我写在 4.3：先给预测和集成链路补边界用例，再谈整体覆盖率抬升。

**问：你的创新点是什么？**
答：不是模型结构上的创新，而是工程上把降级做成了可审计的一等公民——每一段都自带 source、verified 和 simulation 标记，一路透传到大屏。这使得一份带水分的报告和一份诚实的报告，在我的系统里是无法混在一起的。

**问：如果重做一次，你会改哪里？**
答：先定数据契约再写代码。集成链路里预测段一直降级，根因是结果表没有 checkpoint_id 字段，这是我在打通五段之后才发现的契约缺口；如果先设计表结构，这段不会卡到现在。
